# 方案：注册入口 + 统一知识库 + 逻辑隔离多租户

> 版本: V1.0 · 日期: 2026-08-08 · 状态: 待评审
> 前置: Authen 最小核心已部署（auth:8001 / sso:8002 / user:8003 / permission:8004 / gateway:8008），平台 API 已接入 Bearer JWT 校验（0.6.0）

## 1. Authen 能力研究结论（源码 + 实测）

| 能力 | 现状 | 结论 |
|---|---|---|
| 注册 | `POST /api/v1/auth/register/email`（邮箱验证码）/ `register/phone`（手机验证码）；验证码由 `send-email-code` / `send-sms` 发送 | ✅ 可用，但**依赖 SMTP/短信服务**（服务器当前未配置） |
| 登录 | `POST /api/v1/auth/login`，字段 `identifier` + `password` → access_token / refresh_token / sso_session | ✅ 已实测通过 |
| 鉴权 | HS256 JWT，claims: `sub`=user_id, `username`, `email`，`exp`/`iat`/`iss` | ✅ 平台已集成（本地验签） |
| RBAC | permission:8004 完整：角色 CRUD、权限点 CRUD、用户↔角色、`check-permission`、`is-super-admin` | ✅ 可用 |
| 组织（租户载体） | `organizations` 树形表（parent_id/path/level）+ `user_organizations` 多对多 + `organization_permissions` | ✅ 可作为逻辑租户模型 |
| 角色 | super_admin（全权限）、user（`user:read`、`subscription:read`）等 | ✅ 已初始化 |

**关键限制（影响设计）：**
1. JWT 里**没有 tenant/org claim** —— 平台拿不到"用户属于哪个租户"，需要平台侧映射或 Authen 扩展
2. 注册**只建用户，不自动建组织** —— 需要平台注册流程里补"建个人租户"
3. 邮箱/手机注册**必须验证码** —— 没有 SMTP/短信就开不了自助注册（可用超管后台建号替代）

## 2. 场景拆解

```
用户 ──注册──▶ Authen（建用户）──▶ 登录拿 JWT ──▶ 平台 API（验签 + 租户上下文）──▶ 统一知识库
              ▲ 鉴权/RBAC                                              ▲ 逻辑隔离层
```

- **注册入口**：平台提供注册页/API，代理到 Authen；注册时自动为每个用户建"个人组织"（逻辑租户）
- **进来后鉴权**：已有 Bearer JWT 校验；扩展为"从 token 派生租户上下文"，替换当前信任 `X-Tenant-ID` 头的做法
- **底层知识库统一一个**：vault（359 篇 md）+ knowledge_matrix.json 物理共享，不按租户复制
- **逻辑隔离**：数据一份，边界按用户/租户划——见第 4 节

## 3. 总体架构（目标态）

```
┌─────────────────────────────────────────────────────────┐
│ 客户端（Web / API）                                       │
│   注册 → 登录 → 携带 Bearer JWT 调平台 API                  │
└───────────────┬─────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────┐
│ Authen（统一认证，/opt/authen，systemd 5 服务）              │
│   auth:8001 注册/登录/refresh   sso:8002 OIDC             │
│   user:8003 用户管理   permission:8004 RBAC               │
│   gateway:8008 统一入口（含 organization 管理）             │
│   ── 数据: 平台 postgres auth 库 + redis db1              │
└───────────────┬─────────────────────────────────────────┘
                ▼ JWT（HS256 共享密钥验签）
┌─────────────────────────────────────────────────────────┐
│ 平台 API（FastAPI，:8000）                                 │
│   require_auth → 验签 + user_id                           │
│   tenant_context → user → org（个人租户，缓存）             │
│   TenantMiddleware 改造：租户从 token 派生，不再信 header    │
│   ── 知识层（共享）: vault + matrix + chat                 │
│   ── 租户层（隔离）: 会话历史/用量/收藏/配额（带 tenant_id）   │
└───────────────┬─────────────────────────────────────────┘
                ▼
        统一知识库（一份 vault + 一份 matrix）
```

## 4. 核心设计决策：逻辑隔离的三个层次

| 层次 | 含义 | 复杂度 | 建议 |
|---|---|---|---|
| **L1 账号隔离**（必选） | 每个用户独立身份，认证后才能访问；知识库全员共享 | 低 | ✅ 现在就做（认证已就绪） |
| **L2 租户数据隔离**（推荐） | 注册自动建"个人组织"作逻辑租户；平台侧**租户维数据**（会话历史、用量、收藏、配额）按 tenant_id 隔离；知识库仍共享 | 中 | ✅ 现在就做 |
| **L3 文档可见性**（可选） | 知识条目按组织打标（frontmatter `visibility`），检索/问答按用户权限过滤，实现"有的文档只有某些租户能看到" | 高 | ⏳ 预留，二期做 |

**推荐组合：L1 + L2 现在实施，L3 预留接口。**

理由：用户场景是"知识库统一一个 + 逻辑隔离"——L1+L2 满足"身份独立 + 使用边界独立"；L3 会改变检索语义（同一问题不同租户答案不同），需要产品上想清楚，不宜一上来就做。

## 5. 数据模型设计

### Authen 侧（已有，注册时补建）
- `users`：已有
- `organizations`：注册时自动创建 `name=用户名-工作区` 的个人组织
- `user_organizations`：新用户挂到自己的组织
- `roles`：新用户默认 `user` 角色

### 平台侧（新增一张映射表 + 一张租户维表）
```sql
-- 租户映射（缓存 Authen org，避免每次查 Authen）
CREATE TABLE tenant_mappings (
    user_id      UUID PRIMARY KEY,
    org_id       UUID NOT NULL,
    tenant_key   VARCHAR(64) UNIQUE NOT NULL,   -- 逻辑租户标识，如 "org-<uuid前8>"
    created_at   TIMESTAMPTZ DEFAULT now()
);

-- 租户维数据（逻辑隔离的落点：每个租户只看到自己的行）
CREATE TABLE tenant_sessions (        -- 问答会话历史
    id           BIGSERIAL PRIMARY KEY,
    tenant_key   VARCHAR(64) NOT NULL,
    question     TEXT NOT NULL,
    answer       TEXT NOT NULL,
    sources      JSONB,
    created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE tenant_usage (           -- API 用量/配额
    tenant_key   VARCHAR(64) PRIMARY KEY,
    chat_calls   INT DEFAULT 0,
    token_used   BIGINT DEFAULT 0,
    updated_at   TIMESTAMPTZ DEFAULT now()
);
```

### 知识库侧（不变）
- vault + matrix 物理共享；检索函数可接收 `tenant_key` 参数（当前不参与过滤，L3 时用于可见性过滤）

## 6. API 设计

### 注册（新，平台代理）
```
POST /api/v1/register           # 平台新端点（或前端直连 Authen）
  body: { method: "email"|"phone", account, code, username, password }
  流程: 校验验证码（Authen）→ 建用户（Authen）→ 建个人组织（Authen）→ 写 tenant_mappings（平台）
```

### 鉴权（改造现有）
- `require_auth` 返回 payload 后，新增 `get_tenant_context(user_id)`：
  - 查 `tenant_mappings`（缓存优先）→ 无则查 Authen organization → 回填
  - 把 `tenant_key` 写入 `current_tenant`（替换现在的 header 逻辑）
- `TenantMiddleware` 改造：
  - **不再信任 `X-Tenant-ID` 头**（现在是任何人都能传）
  - 租户 = 从 JWT 派生；仅 super_admin 可显式指定租户（`X-Tenant-ID` 保留为管理员覆盖用）

### 新增端点
```
GET  /api/v1/me                  # 当前用户信息 + 租户
GET  /api/v1/me/sessions         # 我的问答历史（tenant 隔离）
POST /api/chat                   # 现有，自动带租户上下文记录会话
GET  /api/v1/me/usage            # 我的用量
```

### 权限接入（RBAC）
- 平台 API 按端点声明权限点：`knowledge:read`、`chat:use`、`admin:*`
- `require_auth` 后调 Authen `check-permission`（缓存 60s）或平台本地映射角色
- 超管可管理所有租户；普通用户只见自己租户

## 7. 实施步骤

### 阶段 1：注册闭环（依赖 SMTP/短信 或 内部开通）
1. 配置 Authen SMTP（`/opt/authen/scripts/configure_smtp.py`）或短信服务；无凭据则先走"超管建号"流程
2. 平台加注册端点（代理 Authen register）+ 登录页/API 调用示例
3. 验证：注册 → 登录 → JWT → 平台 API 200

### 阶段 2：逻辑隔离（L1+L2）
4. 注册流程补"建个人组织 + 写 tenant_mappings"
5. `get_tenant_context` + TenantMiddleware 改造（token 派生租户）
6. 新增 tenant_sessions / tenant_usage，chat 端点落库
7. `GET /api/v1/me` 系列端点
8. 验证：两个用户注册 → 各自会话历史互不可见 → 知识库共享

### 阶段 3（预留）：RBAC 权限点 + L3 文档可见性
9. 平台 API 权限点接入 check-permission
10. 知识条目可见性标记 + 检索过滤（按租户/角色）

## 8. 待确认决策点

| # | 决策点 | 选项 | 影响 |
|---|---|---|---|
| 1 | 逻辑隔离深度 | L1+L2（推荐）/ 含 L3 | 工作量差 ~1 倍 |
| 2 | 注册方式 | 邮箱验证码 / 手机验证码 / 超管建号 | 需要 SMTP/短信凭据 |
| 3 | 新用户是否自动建租户 | 是（个人工作区）/ 否（先只认证） | 阶段 2 前置 |
| 4 | 知识库是否全员共享 | 共享（L1/L2 语义）/ 按租户可见（L3） | 产品语义 |
| 5 | 是否要管理后台 | Authen admin-ui（React，需构建）/ 暂不要 | 资源 2C2G 紧张 |

## 9. 风险与注意事项

- **2C2G 资源**：Authen 5 服务 + 平台三容器已 ~1.2GB；admin-ui（React 构建 + node）不建议上，管理操作走 API
- **验证码依赖**：邮箱/手机注册必须 SMTP/短信；没有就先超管建号，注册入口后置
- **JWT 无租户 claim**：现阶段用 tenant_mappings 表映射；后续若 Authen 扩展 JWT 加 `org_id` claim 可简化（改一处即可）
- **安全**：`X-Tenant-ID` 头信任是当前最大漏洞（任何人可伪造），阶段 2 必须改掉
- **知识库一致性**：共享知识库意味着"一个用户改了知识，所有人看到"——若未来要租户独立知识，预留 `vault/tenants/<key>/` 目录方案，架构不变
