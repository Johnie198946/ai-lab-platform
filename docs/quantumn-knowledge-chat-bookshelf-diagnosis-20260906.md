# Quantumn 知识闭环、聊天恢复与跨系统书架方案

> [!important] 交付边界
> 本文区分代码事实、运行记录、可复现缺陷和待实施设计。未推送、未部署、未上传 iOS。用户原始笔记、定时任务与云端书架未被本次诊断修改。新 UI 为设计演示，不是上线效果。截图缺少 App 构建号，不能用最新源码替代该二进制的事实。

## 一、结论

不是分别再造一个编译器、检索器、同步器。应复用既有链路，补齐原文版本、状态回执、检索覆盖、上架准入及恢复语义。

- 个人手写笔记已有本地保存、云端同步、私有索引及贡献入口；“完全没有机制”不成立。但当前私有索引只是文档目录，不能等同于内容整编完成。
- 知识目标改为 Wiki-first 自生长：保存即来源型 Wiki，自动更新相关主题/实体/综合页，Query 与 Lint 继续积累；词项检索只做导航与过渡。
- 用户最新明确：知识贡献是平台准入必选项。替代旧可选参与产品假设；不等于私人原文公开、追溯授权或自动全文转售。
- 截图对应 Run 实际成功完成。客户端空内容不能直接归因“大模型未返回完整响应”。
- 编号问题是 parser 保留原编号、renderer 又添加编号，且被 bullet 分段后从 1 重新枚举；不是标题级别 1–7 的问题。Markdown 标准标题只有 H1–H6。
- Mac 已有 18:00 Wiki-only 同步；Follow Builders 是独立采集库，既未连接 Vault Writer，也未连接云端书架。
- 原文、保真阅读、注解和蒸馏必须分层；摘要不得顶替原文，也不能因技术上抓到全文就取得转售权。

## 二、架构修正：所有笔记进入可持续生长的 Wiki，而非只增强搜索

### 2.1 为什么上一版偏离了目标

上一版把“目录索引、分词和独立笔记搜索”写成主方案，把 Wiki 整编放成附加流程。这能改善找笔记，却不能保证新知识改进既有知识，也不能保证查询成果留在知识库。现正式改为：**用户手写、导入和 AI 总结保存都是同一 Wiki 生长机制的输入；Wiki 是持久化知识工作面，原始内容是证据底座。**关键词修复仅是存量过渡/导航工具，不能作为最终方案验收。

### 2.2 Karpathy 原始模式与 Quantumn 的工程扩展

用户所指的 kapathy，按 Andrej Karpathy 的官方 `llm-wiki` 原文核验：

- 原始模式是 raw sources、持久 Wiki 和 schema 三层；输入新来源要更新已有实体/主题页、交叉引用、矛盾和综合，而非每次问答重新拼原始片段。
- 操作为 **Ingest / Query / Lint**；Query 的优质新综合可以写回 Wiki；Lint 查矛盾、过时主张、孤立页、缺失概念和资料缺口。
- Query 先读内容型 index，再深入相关 Wiki 页面并带引用综合；log 记录演进过程，不应塞满导航索引。
- 这是模式说明，不是一个名为“Karpathy v4.0”的官方完整产品/算法。原文也允许大规模时选用 qmd 等混合搜索；“不以向量 RAG 为主链”是本产品的明确选择，不冒称 Karpathy 禁止向量。
- 双 Hermes 审核、多租户、准入必选贡献、权限分区、无损阅读、18:00 出版包均是 Quantumn 工程扩展，不归为 Karpathy 原创规定。

原始来源（固定版本）：https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw/6b0cef32d73931fcab7498a7e82208e3ea41ee6f/llm-wiki.md

### 2.3 一套生长机制、不同授权视图，不是两套孤立知识库

```text
手写 / 导入 / AI 总结保存 / 获准采集
→ 固定原文版本与根来源血缘
→ 用户可见的来源型 Wiki 页（保真全文 + 注解区）
→ Hermes Ingest：读相关现有 Wiki，比较断言与证据
→ 创建/更新实体页、概念页、主题页、对比/综合页及双向关联
→ 校验并提交 Wiki + INDEX + 依赖映射 + 生长日志
→ Query 优先读已编译 Wiki，必要时核对来源
→ 有价值的新综合进入同一增量编译流程
→ Lint 持续查冲突、旧结论、缺口，触发有界修订/补证
```

个人和平台使用相同 schema、编译协议、检索路径和 Hermes 执行能力；以 scope 和权限隔离不同视图。个人 Wiki 可以读取获权平台知识进行交叉检验；个人事实不能经链接标题、引用或综合泄漏给其他用户。平台只接收通过治理的贡献派生，不直接获得其他租户 raw 的任意读取权限。

**每篇笔记都是可参与生长的 Wiki 来源节点，不等于每篇笔记都立即成为公共可信事实。**个人观点、猜想也能以 opinion/hypothesis/provisional 类型进入个人 Wiki；已核验的 canonical 断言另有证据要求。空稿、恶意附件、格式异常可以明确 blocked，不能悄悄漏编。平台现有置信度准入规则继续适用，不因保存或必选贡献自动提级。

### 2.4 无损与 Wiki 改写不冲突

- 用户笔记原文版本不可被模型覆盖；来源型 Wiki 页默认包含所有独有原文，不是只有综述或一个隐藏附件链接。
- 概念/主题/综合 Wiki 页允许模型持续重写、去重和重组，因为它们是派生知识；所有断言仍要溯源，不能把派生更新当作原笔记合并。
- 用户手工编辑派生 Wiki 时，将编辑记录为新的用户来源版本/补丁，明确用户原话区和 AI 维护区；用户文字不能被下一轮编译静默覆盖。
- 全文合并另走已确定的逐块覆盖、来源固定版本、附件完整性、CAS 与旧新入口统一门禁。

### 2.5 交叉检验与生长的具体动作

保存后自动异步 Ingest，不再让用户每篇点击“编译”。Hermes 必须先读已有相关 Wiki 与其证据，再输出这些结果之一或组合：

| 判断 | Wiki 变化 | 证据约束 |
|---|---|---|
| 新事实/方法/关系 | 补现有 canonical 页，必要时新建实体/概念页 | 写明根来源、适用条件和时间 |
| 独立佐证 | 给已有断言增加证据与核验说明 | 必须是独立根来源，不按文档数量加分 |
| 同源重述 | 增加可追溯引用或 no-op | 同一文章的笔记/AI 摘要/平台转述不算三份证据 |
| 冲突/反例 | 保留双方，新增矛盾区和待核验问题 | 不以最新、多数或模型偏好强行覆盖 |
| 已过时 | 标注被什么证据、何时、在哪些条件下替代 | 原始历史和来源仍可追溯 |
| 新综合/推断 | 更新综合页，标记 inference 和依赖 | 可提升组织价值，不自动增加事实可信度 |
| 资料不足 | 留待证问题和补证任务 | 不生成空壳事实，不伪造外部验证 |

写入收据应展示更新了哪些已有页面、为何新增页面、增加哪些证据/冲突、哪些链接被修改、哪些项失败或无增量。不能只报“索引成功”。关系类型与支持它的段落须对应；links 可以组织知识，但“相关”不等于相互证明。

### 2.6 现有代码：复用可信部分，不复用宣传性注释

本轮读取发现：

- `knowledge_sync.py` 与 `user_note_context.py` 已有保存及私有目录索引，但不能证明 Wiki 跨页编译完成。
- `backend/api/knowledge.py:_search_docs` 已有 Wiki 标题/别名优先、wikilink 追读、matrix 辅助的基础，应该扩展到授权个人 Wiki 视图，而非再造私人关键词搜索主链。
- `CompilerService.apply_verified_increment` 已有来源依赖、root_source_fingerprint、CAS、no_increment/conflict 约束，可作为验证后应用的基底。
- 同一文件的旧 `raw_to_wiki/_update_wiki_from_raw` 路径仍有读取片段、插入 summary、创建“未命名实体”等简化逻辑；其“完整实现”注释不是能力证明。它不能作为生产自生长验收依据。
- `knowledge_contribution.py` 已有源事件、根血缘、授权版本、撤回传播、待重编投影等可复用机制；已读本地分支仍允许 participation_enabled=false，不能宣称必选准入已部署。

实施前进一步定位线上实际路由，保留薄兼容适配，将旧写入收敛到现有 Hermes 编译和验证后提交路径。不得直接启用旧 llm_client 回调形成第二 AI Runtime。

### 2.7 运行与一致性合同

- 单一原文保存入口；source_id + revision + hash 固定输入，编辑防抖但每个确认版本可追溯。
- 事件幂等按 scope + source_revision + compiler_contract；按知识空间/目标页串行提交或 CAS，避免并发编译互相覆盖。
- Hermes 管理 AI session、工具、上下文、续接与 checkpoint；业务层只管理准入、内容版本、编译请求及 receipt/event 投影。
- 一次生长会改多页：生成变更集，全部校验后切一致版本；失败不只更新 INDEX 或部分正文。原文保存不受模型故障阻塞。
- INDEX 内容型、分域分层；COMPILE_LOG/log 追加型；矩阵和依赖索引由已发布 Wiki 生成，不成为第二正文真源。
- 页面/断言绑定根来源、父事件、版本、编译器、适用范围、证据状态；快照、差异和撤回可复现。

用户状态为：**原文已保存→Wiki 正在更新→Wiki 已更新/存在待核验冲突/更新失败待重试**。展示可展开的生长变更记录，而不是要求用户管理编译内部流程。

## 三、Wiki-first 查询、Query 回写与 Lint 自生长

### 3.1 正式查询主链

```text
身份与可读 scope
→ 内容索引 INDEX / 分域目录 / 既有 matrix 导航
→ 找到 canonical、来源型与综合 Wiki 页
→ 读取相关页正文、主张、矛盾与来源依赖
→ 按问题沿真实 wikilinks 有界追读
→ 必要时返回获权原始版本核验
→ 带页/段/来源版本引用的综合回答
→ 新增综合候选交给同一 Wiki 编译门禁
```

不是把所有笔记全文扫一遍打分后拼几个片段。词项/全文搜索用于找 Wiki 页、消歧和兜底，不能替代 Wiki 编译；无向量 RAG 主链。规模扩大时使用分层索引、可重建的词项索引及有界关联追读，不把整个 INDEX/全库塞进上下文。

现有 `user_note_search` 保留名称兼容，但内部路由到同一 Wiki-first 服务的用户授权视图；`knowledge_search` 和 `knowledge_workspace_read` 也用同一页面 ID/版本/权限契约。不再发展另一套独立笔记检索器。

“我之前研究过什么”先读个人来源型 Wiki、研究综合页与演进日志，平台页帮助交叉解释但不能冒充用户旧研究。尚未编译的最新笔记可明确以 source-only 状态补读并触发编译；它是可见降级，不是正式路径被悄悄切回 raw 搜索。

### 3.2 Query 也要积累知识

有新比较、概念关系、研究综合或明确纠正的回答自动进入候选队列，经同一语义审查和来源门禁后更新已有 Wiki 或新建真正需要的综合页；不是每次聊天存一篇新文章。

- 同样问题重复问：复用已有综合，版本不变时 no-op。
- 基于已有材料得到推断：标为新综合，不当独立证据增加置信度。
- 用户补充经验/纠正：保存为带作者与时间的新来源，后续核验；模型不能因用户坚持直接改事实。
- 无实质增量、寒暄、失败输出、运行日志、密钥不进入 Wiki。
- 答案先返回；异步写回失败单独显示，不把回答成功等同编译成功。

### 3.3 Lint 驱动持续检验，而非只查断链

复用现有 Writer/Evolution/治理调度入口，事件增量检查与周期检查结合。任务包括：跨页矛盾、过时证据、缺来源的断言、同源多次增信、孤立页、重复 canonical、缺失概念、断链、权限漂移与来源撤回。

输出有证据的变更建议或补证问题。对权限内、非破坏性的派生更新可自动完成；用户原文改写/合并仍需要明确授权。外部补证有范围、预算、频率和失败退避，不能无限搜索。无新证据不反复改写、不提高置信度。

### 3.4 防止假自生长

Wiki→回答→新 Wiki→再次回答只是一条相同血缘链，不是多个独立来源。使用 root_source_fingerprint、父子事件和依赖图阻止循环增信；多 Agent 互相同意也不是外部佐证。增长可以表现为更好的解释、索引、反例和关联，不强求页数或字数增长。

若材料全部指向同一个最初来源，即使有多个用户贡献，也只算该根来源的不同表达；独立用户经验是否能计为独立证据需核验采集背景，不能只凭不同 user_id。

### 3.5 必选贡献作为平台准入条件（用户最新决议）

**替代旧版“进入平台后可自愿开启贡献”的产品假设。**新用户须明确接受版本化知识贡献协议后，才能使用受该协议约束的平台服务。后端准入验证覆盖 App、Web、API 和旧客户端，不能只有前端必选框。不预勾、不冒填同意时间，不把本次产品决议当作所有租户已经签约。

- 入场接受协议后，授权生效范围内的手写/AI 保存及合格使用内容自动进入贡献处理，无需逐笔开启开关。
- 必选的是合法范围内的贡献处理机制，不是所有内容直接公共化；原文默认私有，平台获得经过治理的派生知识。
- 复用双 Hermes 独立脱敏/事实审核和反识别校验；两个审核通过只证明门禁结果，不构成两份独立事实证据。
- 保留日志/密钥、第三方个人信息、版权和其他无权贡献内容的排除；现有文件级退出规则不因准入必选而默认取消。若商业规则拟取消，须单独明确范围并完成隐私/法律审查，不能偷偷扩大此次授权。
- 不追溯生效前内容；历史个人笔记可以补建个人 Wiki，贡献历史内容则需明确、可证明的历史范围授权。
- 老用户须有协议版本升级及重新接受流程，不能后台把 false 改 true；保留导出、删除、撤回和账户处理通道，不以退出为由扣留自有资料。
- 用户撤回准入协议后停止新贡献，并按既定撤回规则处理依赖；不再满足平台准入条件时停止相应正常服务，不继续提供旧版“关闭贡献但照常使用全部平台”分支。资料权利处理与账号退出服务分开。
- 事实准入、可被其他租户查询、商业上架/全文再分发是后续独立门。必选贡献不自动授予出售私人原文或第三方课程的权利。

技术上保留“原文保存/Wiki 更新”和“平台贡献”的异步失败隔离，是避免数据丢失和部分失败，不是保留可绕过准入的可选贡献产品。

### 3.6 存量迁移与验收改版

迁移顺序：盘点全部来源/原笔记版本→创建来源型 Wiki→按主题读已有页并交叉检验→更新实体/综合页、INDEX、日志与依赖→切查询到统一 Wiki-first→旧搜索仅作可观测回退。保留旧 ID 映射、原文与回滚快照，不批量压缩覆盖。旧未接受新协议用户先走准入迁移，不以数据迁移伪装贡献授权。

必须用以下场景验收，不能以“搜得到标题”代替：

1. 新建手写笔记、AI 总结分别自动形成来源型 Wiki，并更新真正相关的已有主题页。
2. 两份独立材料相互佐证；同一材料的多份摘要不重复增信。
3. 新材料反驳旧结论，Wiki 保留冲突、范围和证据，而非静默覆盖。
4. 查询跨多个 Wiki 页回答并引用；有价值的新综合能回写，重复问答 no-op。
5. 新编辑/删除/撤回触发受影响派生重编，不误删其他独立来源。
6. Lint 找出真实过时断言、孤立页、证据缺口并给可验证处理结果。
7. 同一编译重试不多建页；多页失败不发布半份 Wiki；原文逐块及附件完整。
8. 不同用户原文不可串读，平台合格派生可在合法授权范围复用；相互关联不能泄漏身份。
9. 未接受准入协议无法使用受约束平台服务；接受后自动处理范围内贡献；老用户不被默示改为同意。
10. UI 展示实际 Wiki 变更、待核验冲突和失败；无法完成时明确 source-only，不假报 Wiki 已生长。

指标以有证据的有效更新、冲突发现/解决、来源完整性、检索引用正确率、重复 no-op 和污染/越权失败为准，不以新增页面数、链接数或模型一致率代替知识质量。

### 修复原则

- 用户执行态以同一个 run_id 的持久状态为准，断连/切屏不是任务失败。
- 状态未知、正在恢复、后台 running、真实 failed、completed 但空结果分开；空文本不是独立失败状态。
- 优先按 run_id 重放事件/获取终态内容；恢复按钮不使用 regenerate，不重发原始业务请求。
- 只有明确失败的 run 才显示失败原因；真实空终态给可诊断错误码，保留原记录，不无限重试。
- 流式 done、轮询完成、历史加载、tab 返回必须共享归属与版本校验。旧 run/旧 request/旧 tenant epoch 的事件不能覆盖新消息。
- 不能只改提示文案就宣布恢复链路修复；应真实跑恢复回归。

公开进度展示只用执行事件、已完成步骤、当前状态与高层说明，不展示私有内部思维链，也不伪造进度比例。

| 层 | 面向用户 | 规则 |
|---|---|---|
| 原始证据 | 获权的 PDF/EPUB/HTML/原文快照 | 固定版本、保留附件、准确作者和链接；不暴露文件系统 raw 路径 |

#### F. 撤权与版本传播

在线读取实时检查。离线缓存无法承诺即时远程消失，应有加密、短期授权租约与到期不可读规则，在购买前说明离线期限。重试包绑定授权版本与有效期，迟到事件不能复活撤回内容。上架、撤权、重试全部幂等。
