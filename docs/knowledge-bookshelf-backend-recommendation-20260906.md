# 知识书架后端与内容治理建议

## 结论

“书”应当是现有 Wiki 知识的读者视图，而不是新增一套内容仓库。继续以 `raw → 研究系统 → wiki` 作为事实链，以 catalog/policy 作为发布与授权投影；书架只消费投影结果。这样不会制造第二份正文，也不会绕过红黄绿权限。

## 已核验的现状

- Vault 共约 2,098 篇 Markdown：`raw` 906、`wiki` 272、`研究系统` 197、`knowledge` 33、`产品设计` 118。
- `knowledge_matrix.json` 有 268 个文档、714 个实体，适合做索引，不应作为正文真相源。
- 272 篇 Wiki 中，安全色主要为 Green（266）；Yellow 为 0。作者、概要、订阅权益字段基本缺失。
- 严格 `knowledge_catalog.json` 只收录 11 篇且生成时间较旧；当前运行时代码会再合并已批准的颜色投影，实际可形成约 259 本可见“书”。两条准入尺度必须统一，否则后台统计与用户看到的书会不一致。
- Vault 中关于“外部发布已全部放开”的文字标记为设计/开发声明；当前代码仍以 `knowledge_policy.py` 的租户、权益与 capability 校验为准。Vault 内的流程说明仅作为资料分析，没有被当作本次开发指令。

## 红黄绿在书架中的准确含义

| 颜色 | 书架可发现性 | 点开后 | 订阅关系 |
|---|---|---|---|
| Green | 可公开展示 | 可读概要与批准内容 | 可作为免费样书/基础权益，不应伪装成稀缺付费内容 |
| Yellow | 只展示经过脱敏、单独批准的营销卡片 | 无权益时不返回正文、内部摘要或源文件元数据 | 由 Authen 的精确 `entitlement_key` 解锁；钱包偏好不能授权 |
| Red | 不进入公共搜索、推荐或订阅市场 | 仅 owner tenant/受控管理员可见 | 不售卖，不把“订阅”当作 Red 授权手段 |

颜色是内容治理标签，不是安全边界。真正的边界仍是服务端策略、租户隔离、时效校验和短期签名 capability。

## 推荐数据流

```text
raw（不可变证据）
  → 研究系统（整理与编译）
  → wiki（唯一正文真相源）
  → 治理审批（颜色、K 级、来源、状态）
  → catalog / matrix（准入与索引投影）
  → bookshelf API（书架、书目、读者概要）
  → policy + Authen entitlement（详情读取授权）
```

不要新建 `books/` 正文目录，也不要把 Wiki 全文复制进数据库。书架 API 只返回展示所需字段；详情读取继续穿过同一个权限入口。

## 书的数据模型

下一步应在 Wiki frontmatter 补齐最小发布字段，而不是增加新的 service/repository：

```yaml
book_title: 面向用户的书名
book_author: 经编辑核实的书籍署名（可覆盖自动归因）
book_summary: 80–160 字、已批准的读者概要
shelf_id: product
cover_theme: violet
edition: 2026.09
sample_excerpt: 可公开试读片段
entitlement_key: yellow 内容的精确权益键
```

`book_title/book_author/book_summary` 是编辑事实，不能靠正文中出现的人名猜测。当前作者链路为：Wiki `book_author` → Raw `source_author/author/authors/creator/byline/publisher` → Raw 前 80 行明确作者行 → 单一官方域名映射 → `Quantum 研究团队`。后端同时返回 `author_source`，便于区分原文署名、编辑署名与自研兜底。

对当前 259 篇已批准 Wiki 的实测是：7 篇能从现有 Raw 来源字段安全归因，252 篇暂无可追溯署名。这不是解析失败，而是 Vault 历史元数据缺口；应先补首批 6–12 本主题书，不应用 LLM 大规模猜作者。

## Markdown 没有图片时如何自动生成封面

第一版不应该为每篇 Markdown 调用生图模型。书架需要的是稳定的视觉身份，而不是 259 张昂贵、风格漂移且难以审核的插画。本次实现采用纯 SwiftUI 的程序化封面：不写 PNG、不依赖网络，离线也能生成。

### 生成输入与规则

```text
knowledge_id ─SHA-256→ cover_variant（0…5，决定几何纹样）
pack/type ─────────→ cover_theme（决定同一书架的色彩家族）
book_title ────────→ 封面主标题
book_author / Raw 来源链 → 可追溯作者；缺失时为“Quantum 研究团队”
cover_version ─────→ 当前算法版本 1
```

- 同一分类使用同一色彩家族，让用户一眼识别系列；单本书再由稳定哈希选择圆环、旋转方框或线性纹样。
- `knowledge_id` 不变，封面就不变；正式出版的 Wiki 必须显式保存稳定 `knowledge_id`，否则当前按路径生成的兜底 ID 会在文件改名后变化。
- 标题与作者始终是封面的一部分，因此即使颜色相近也能区分，且 VoiceOver 直接读取书名和作者。
- 几何纹样只是装饰，已从辅助功能树隐藏；文字覆盖深色渐层以维持对比度。
- 编辑可以在 Wiki 中用 `cover_theme` 覆盖自动分类，但值被限制为安全的短 slug；不能传任意 CSS、URL 或文件路径。
- `cover_variant` 和 `cover_version` 由服务端返回。未来升级算法时保留旧版本渲染，避免已出版书籍突然“换脸”。

### 自动封面的三层策略

| 层级 | 使用场景 | 做法 |
|---|---|---|
| 程序化封面 | 所有 Wiki 条目、长尾书目 | 当前默认；零生成成本、即时、稳定、无需图片资产 |
| 编辑模板封面 | 首批 6–12 本正式主题书 | 仍使用程序化布局，但人工选择主题、短标题、副标题和系列编号 |
| AI 插画封面 | 首页主推或付费旗舰书 | 仅在程序化封面已验证转化不足时增加，不能作为默认流水线 |

### 如果以后接入 AI 生图

只向模型发送经过 Green/Yellow 营销审批的短标题、公开概要、分类和品牌风格提示，不发送 Raw、Wiki 正文、来源文件、客户名或 Red 内容。生成后必须经过人工审核，再把批准资产上传对象存储，并记录：

```yaml
cover_asset_url: https://受控对象存储/...
cover_asset_sha256: ...
cover_prompt_version: 1
cover_approved_by: ...
cover_approved_at: ...
```

客户端优先显示批准图片；下载失败时立即回退到相同的程序化封面。不要在用户打开书架时同步调用生图服务，也不要为每次内容更新重新生成封面。只有书名、定位或版本发生实质变化时才创建新封面候选。

## 内容产品策略

不要把 259 篇 Wiki 一篇一书地出售。第一批只策划 6–12 本“主题书”，每本聚合若干已批准页面，并明确一个用户承诺，例如“半小时理解某竞品的商业模式”。

- Green：封面、概要与一章样读，承担获客和信任证明。
- Yellow：形成真正的会员书，围绕决策价值、更新频率和独家整理售卖，而不是单纯按文档数量收费。
- Red：完全退出营销目录。
- 每本书显示版本、更新时间、来源数量和适用人群；这些信号比“共 78 篇”更能促成订阅。
- 订阅页衡量 `书架曝光 → 书封点击 → 样读完成 → 申请订阅 → 获批/付费`，按书而不是按文件夹统计。

## 订阅后在哪里：放进“笔记”，但不复制整本书

> 实施状态（2026-09-06）：用户级订阅关系、取消订阅、我的书架和阅读进度 API 已完成；iOS“笔记”页已接入“我订阅的书”，概述可生成用户自有的 Obsidian Markdown 笔记。完整章节阅读与段落级选择摘录仍待书籍正文 API。

用户的直觉是对的：订阅的书应进入底部“知识”中的笔记主页，而不应继续藏在设置页。但它应是一张“只读订阅书卡”，不是把整本 Wiki 复制成用户可编辑 Markdown。

推荐交互：

1. 用户在书籍沉浸页看封面、概述、目录和样读，点“订阅并加入笔记”。
2. 服务端记录 `user_book_subscription(user_id, tenant_key, book_id, edition, subscribed_at, last_read_at)`；Yellow 仍必须通过 Authen 精确权益。
3. 笔记首页顶部新增“我订阅的书”横向书架，下方仍是“我的笔记”；搜索同时覆盖两者。
4. 点书卡进入只读阅读器，显示版本更新、阅读进度和新内容标记；不跳回设置页。
5. 用户选中段落后可“摘录到笔记”：新建用户自有 Markdown，自动附加书名、作者、版本、Wiki block ID 与原始来源。书后续更新不覆盖用户摘录和批注。

数据上只保存“订阅关系 + 阅读进度”，客户端的订阅书卡是投影。这样一处更新 Wiki，所有订阅者看到新版，不会生成几百份已过期副本。

## 书里展示 Raw 还是加工内容

默认展示 **Quantum 基于 Wiki 的编研版**，不直接展示 Raw 全文。Raw 是证据层，常包含抓取噪声、重复内容、不稳定格式、内部备注或不可再发布内容；将它直接当书籍正文，会同时降低阅读体验和放大版权/泄密风险。

建议将阅读器分为三层：

- **正文层**：已批准 Wiki 的 Quantum 编研内容，包含概述、结论、结构化章节、反例与适用边界。
- **引用层**：每个重要结论显示作者、出版时间、来源类型和可验证引用；点引用打开“来源卡”。
- **原文层**：只有当 `external_publish_allowed=true`、授权明确且内容已清洗时，才提供“查看原文”；否则只提供外部原始 URL、短引文或不可见的证据编号。Red 永远不向公共订阅者暴露 Raw。

明确作者时，封面可用原作者署名，但正文页必须标注“Quantum 编研”，不能让用户误以为原作者撰写了 Quantum 新增的总结、判断或章节。

## 实施优先级

1. **P0：统一准入。** 明确 sellable book 是否必须满足 approved + Green/Yellow + K5 + 活跃 + 来源阈值，并让静态 catalog、运行时 projection、统计口径共用同一规则。
2. **P0：补发布元数据。** 为首批 6–12 本书人工填写作者、概要、样读和封面主题；Yellow 必须补 `entitlement_key`。
3. **P0：制作真实 Yellow 库存。** 当前 Yellow 为 0；若没有可售内容，再漂亮的书架也不会提升订阅。
4. **P1：拆分列表与详情。** 当前约 259 本可由单个响应承载；超过 300 本或响应约 250 KB 时，再增加分页和独立详情端点。
5. **P1：编辑与指标闭环。** 建立出版审核、下架、版本更新以及转化漏斗仪表盘。

## 本次实现边界

本次新增的是既有 catalog 的读者投影和 SwiftUI 书架界面，没有新建存储层、权限体系或第三方依赖。Yellow 的营销书仍来自 Authen 知识包；Yellow Wiki 的未批准元数据不会通过书架接口泄露。
